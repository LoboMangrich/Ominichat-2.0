## Story

**Como** operador da plataforma Ominichat,
**eu quero** que os endpoints de webhook do WhatsApp/Instagram (Meta) e do Telegram validem a
assinatura de cada requisição POST,
**para que** mensagens, contatos e automações não possam ser injetados por qualquer requisição
anônima da internet.

## Acceptance Criteria

1. `server/_core/index.ts` captura o raw body de cada requisição (via opção `verify` de
   `express.json()`) e o disponibiliza como `req.rawBody` (Buffer) antes de qualquer parsing, sem
   quebrar os handlers existentes que leem `req.body`.
2. Existe `server/_core/webhookAuth.ts` com verificação por provedor, expondo ao menos
   `verifyMetaSignature(req)` e `verifyTelegramSecret(req)`.
3. `POST /api/webhooks/whatsapp` e `POST /api/webhooks/instagram` (Meta) respondem 401 para
   qualquer requisição cujo header `x-hub-signature-256` não bata com o HMAC-SHA256 do raw body
   usando o App Secret (`META_APP_SECRET`). Se o segredo não estiver configurado, a rota falha
   fechada (401) e loga o problema — nunca aceita por omissão.
4. `POST /api/webhooks/telegram` responde 401 para qualquer requisição cujo header
   `x-telegram-bot-api-secret-token` não bata com o segredo configurado
   (`TELEGRAM_WEBHOOK_SECRET`), com o mesmo comportamento fail-closed do AC 3.
5. O fallback hardcoded `"cs_platform_verify_token"` em `server/webhooks.ts:641` é removido. Se
   `WHATSAPP_VERIFY_TOKEN` não estiver definido, o handshake GET falha fechado (403), nunca aceita
   um token adivinhável.
6. Toda comparação de segredo em `webhookAuth.ts` usa `timingSafeEqual` com checagem de tamanho
   antes da comparação — mesmo padrão de `safeCompare` em `routeGuards.ts:38-44`.
7. `.env.example` documenta as novas variáveis (`META_APP_SECRET`, `TELEGRAM_WEBHOOK_SECRET`) sem
   valores reais.
8. Testes automatizados cobrem, para Meta e Telegram: assinatura válida aceita; assinatura
   ausente ou incorreta rejeitada (401); segredo não configurado no ambiente rejeita
   (fail-closed).
9. **Fora do escopo desta story:** Pagar.me, Digital Manager Guru, GoHighLevel, Z-API e Evolution
   API. Cada um tem mecanismo de assinatura próprio que precisa ser confirmado na documentação do
   provedor antes de implementar (CLAUDE.md > Prioridades > 1). Cada provedor vira uma story
   subsequente (1.2, 1.3, ...) — não inventar o mecanismo aqui.

## Dev Notes

### Contexto do problema

Nenhum dos 15 endpoints POST em `server/webhooks.ts` valida assinatura hoje. O único mecanismo
existente é `hub.verify_token`, que cobre apenas o handshake GET da Meta — os POSTs, onde as
mensagens realmente chegam, aceitam qualquer requisição anônima.
[Source: CLAUDE.md > Prioridades atuais > 1]

### File Locations (verificado no código atual, 2026-08-18)

- `server/_core/index.ts:37-38` — `express.json({ limit: "50mb" })` e
  `express.urlencoded({ limit: "50mb", extended: true })` **sem** opção `verify`. O raw body é
  descartado antes de chegar em `webhooks.ts`.
  [Source: server/_core/index.ts:37-38]
- `server/_core/index.ts:41` — `registerWebhooks(app)` é montado **antes** do tRPC, então a
  proteção padrão do tRPC não cobre nada em `webhooks.ts`.
  [Source: server/_core/index.ts:41]
- `server/webhooks.ts` — os 15 endpoints POST existentes (linhas de referência no momento desta
  story): guru:249, ghl:438, instagram:543, telegram:590, whatsapp:652, pagarme:782,
  email-ticket:862, poll-email:894 (já usa `requireCronAuth`), send-scheduled:907 (já usa
  `requireCronAuth`), upload:1002 e upload-media:1018 (já usam `requireSession`), zapi:1044,
  evolution:1093, e os demais `/api/scheduled/*` (já usam `requireCronAuth`). Os endpoints em
  escopo desta story (whatsapp, instagram, telegram) ainda não têm nenhum guard.
  [Source: server/webhooks.ts]
- `server/webhooks.ts:641` — fallback hardcoded:
  `const VERIFY_TOKEN = process.env.WHATSAPP_VERIFY_TOKEN || "cs_platform_verify_token";`
  [Source: server/webhooks.ts:641]
- `server/_core/routeGuards.ts:38-44` — padrão existente de comparação segura já usado no
  projeto (`safeCompare`), a reaproveitar/espelhar em `webhookAuth.ts`:
  ```ts
  function safeCompare(a: string, b: string): boolean {
    const bufA = Buffer.from(a);
    const bufB = Buffer.from(b);
    if (bufA.length !== bufB.length) return false;
    return timingSafeEqual(bufA, bufB);
  }
  ```
  [Source: server/_core/routeGuards.ts:38-44]
- `server/_core/env.ts` — objeto `ENV` centraliza variáveis de ambiente; as novas variáveis desta
  story devem seguir o mesmo padrão (`process.env.X ?? ""`).
  [Source: server/_core/env.ts]

### Padrões do projeto a seguir

- Middlewares de auth novos são **fail-closed**: se o segredo não estiver configurado, a rota
  nega. Nunca abre. [Source: CLAUDE.md > Convenções]
- Comparação de segredos sempre com `timingSafeEqual` e checagem de tamanho antes.
  [Source: CLAUDE.md > Convenções; server/_core/routeGuards.ts:38]
- Comentários e mensagens de erro voltadas ao usuário em português; nomes de código em inglês.
  [Source: CLAUDE.md > Convenções]
- Segredos apenas por variável de ambiente — nunca fallback literal no código (o repositório é
  público). [Source: CLAUDE.md > Segurança]
